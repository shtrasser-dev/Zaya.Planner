# Zaya Planner: family schedule and house plan

Design of the next part of Zaya Planner, agreed before writing code.
What exists today (task store, executor, `plan_window`, `ensure_state`) is described in the
[README](../README.md); this document is about what is built on top of it.

## 1. Goal

The family plans its days; the house follows.

- Each person has a calendar: school and clubs for children, work and appointments for adults.
- Some events are trips: someone has to drive someone somewhere by a given time.
- From trips the planner works out **departures** and **wake-ups**; from those the house plans
  its work: the car is charged before the first departure, the floor is warm by the wake-up.
- A change in a calendar (a lesson moved, an appointment added) changes the plan right away.
- Everything the house is going to do, and why, is visible in one place: the **house plan**.

Principles:

- Nothing is decided by matching text. Trips, wake-ups and their links are real data fields.
- No logic is hard-wired per person or per device: what heats which floor, who is woken,
  which car is charged is set up with standard Home Assistant tools (automations,
  device settings).
- What can be computed is computed; the person only says what they know (“school at 8:00,
  I drive, 40 minutes on the way”).

## 2. Example: an ordinary weekday

Masha's timetable: Monday school 8:00–13:45. Monday is “take there” by Dad on the Leaf,
40 minutes on the way; “pick up” by Mum on the Chery.

The house plan for Monday, worked out the evening before:

```
02:10–06:50  Leaf charging          ← departure 7:20 (first Leaf departure of the day)
06:00–06:40  Floor heating          ← wake-up 6:20 (Dad)
06:20        Wake-up (Dad)          ← departure 7:20 − getting ready 60 min
07:20        Departure on the Leaf  ← School 8:00 (Masha), Dad drives, 40 min
08:30        Wake-up (Mum)          ← her weekday wake-up
13:05        Departure on the Chery ← School ends 13:45 (Masha), Mum drives, pick up
```

In the evening Dad's Android phone gets an alarm for 6:20.
If the lesson moves to 9:00 (only this Monday), the plan moves with it.

## 3. Concepts

### 3.1 People

People come from Home Assistant **People** (Settings → People); children are added there
without a login. In Zaya Planner's settings the user picks who takes part.

Each person becomes a **device** “Zaya: Name” whose settings are ordinary entities
(editable on the device page and on any dashboard):

| Setting | Example | Meaning |
|---|---|---|
| Getting ready | 60 min | Wake-up generated by a trip is this long before the person's departure |
| Wake up for trips | on / off | Whether trips create wake-ups for this person (off for small children today) |
| Cars | Leaf | Cars this person drives; the first one is the default for their trips |
| Usually drives | Dad | For children: who is added to their trips by default |
| Alarm phone | Pixel / none | Android phone that gets the alarm for the wake-up (see 3.9) |
| Set alarm at | 21:00 | When the alarm for tomorrow is set |
| Calendar | “Masha” | The person's calendar, created by the integration |

Whether a person is an adult (can drive) follows from the settings: a person with cars is a driver.

### 3.2 Cars

Each car is a device “Zaya: Leaf” with settings: charger switch (none for the Chery),
how long before the departure charging must end. One car may belong to several people.

### 3.3 Person calendars

Zaya Planner provides one calendar per person (`calendar.zaya_<person>`). They are ordinary
Home Assistant calendars: visible in the Calendar panel, usable in calendar triggers,
editable there (basic fields). Events are stored in iCalendar (`.ics`) with the same
library Home Assistant's Local Calendar uses, so recurrence, exceptions and
“only this event / this and following” work as in Local Calendar.

Fields of an event besides the standard ones are stored as iCalendar `X-` properties:

| Field | Property | Values |
|---|---|---|
| Kind | `X-ZAYA-KIND` | `event` (default), `wake`, `cancel` |
| Trip | `X-ZAYA-TRIP` | none, `drop` (take there), `pickup`, `both` |
| Riders | `X-ZAYA-RIDERS` | people going |
| Driver | `X-ZAYA-DRIVER` | a rider who drives |
| Car | `X-ZAYA-CAR` | a car |
| Travel time | `X-ZAYA-TRAVEL` | minutes, including parking |
| Lessons | `X-ZAYA-LESSONS` | list from the weekly timetable, information only |
| Timetable | `X-ZAYA-TIMETABLE` | id of the weekly timetable the event came from |

Google Calendar is not used as storage. A one-way export may be added later (section 8).

### 3.4 Events

- **Ordinary events** (work, doctor, “the plumber comes”) are markers: by themselves they
  create nothing. Automations can be tied to them (section 3.8).
- **Trips** are ordinary events with a trip:
  - *Take there*: departure = start − travel time.
  - *Pick up*: departure = end − travel time.
  - *Take there and pick up*: both; the driver comes home in between.
  - Defaults: riders = the calendar's owner + the person who usually drives them;
    driver = the only driver among riders (asked only when there are two);
    car = the driver's default car; travel time = from the last trip with the same title.
- **Wake-ups** are events of kind `wake` (see 3.6).
- **Cancellations** are events of kind `cancel` (“Frost”, “Vacation”, “No first two lessons”):
  they switch off what happens in their time *in the same person's calendar*, without
  deleting anything. All-day or with times, one day or many. Within a cancellation:
  - an event entirely inside it does not happen: no trips, no wake-ups from it;
  - an event that starts inside it starts when it ends (the “take there” departure moves later);
  - an event that ends inside it ends when it starts (the “pick up” departure moves earlier);
  - a wake-up inside it is cancelled.

  Cancelled events stay visible (greyed out) so it is clear why the house is quiet.
  Deleting the cancellation brings everything back. A dashboard button
  “No school tomorrow” creates an all-day cancellation for the children.
  Public holidays from the Workday integration may later count as cancellations (optional).

### 3.5 Weekly timetables

School and clubs are entered as a **weekly timetable** instead of single events:

```
School — Masha                 period 01.09.2026 – 31.05.2027, travel time 40 min
       Start   End     Take there    Pick up       Lessons
Mon    08:00   13:45   Dad · Leaf    Mum · Chery   Maths, Russian, …
Tue    08:00   14:40   Dad · Leaf    —             …
…
Sat    09:00   11:35   —             —             …
```

The timetable produces one weekly recurring event per row in the child's calendar
(“School”, with trips and lessons). Changing the timetable rewrites those events;
a change on one day is made on that day's event only. Days off, vacations and cancelled
lessons are cancellations in the child's calendar (see 3.4).

### 3.6 Wake-ups

A person's wake-ups come from two sources:

1. **Set by the user**: an event of kind `wake` in their calendar, usually recurring
   (“Mum: wake-up 8:30 on weekdays”).
2. **Created by trips**: for every rider with “Wake up for trips” on,
   wake-up = their departure − their getting-ready time.

The person's wake-up of the day is the **earliest** of them. “Don't wake me today” = delete
that day's wake-up event; “wake me at 6:00 tomorrow” = move it. Generated wake-ups follow
their trips and are not edited by hand.

### 3.7 House plan and anchors

The integration keeps the plan for today and tomorrow up to date and shows it as a
read-only calendar **“House plan”**: departures and wake-ups with their reasons, and the
tasks of the planner with their outcome (✅ ⚠️ ❌). It is recalculated when a person
calendar changes (calendar event subscription), when a setting changes, at midnight and
after a restart.

Anchors are sensors (timestamps) that rules use:

- `sensor.zaya_<person>_next_wake_up`, `sensor.zaya_<person>_next_departure`;
- `sensor.zaya_house_first_wake_up` (earliest wake-up in the house);
- `sensor.zaya_<car>_first_departure` (the car's first departure of the day:
  the car is charged once a day for it; a second charge is set by hand).

### 3.8 Rules

Rules stay ordinary automations, made with the visual editor: the trigger **“Zaya Planner:
time to plan”** (it fires after a start, when automations are saved, when a task ends, when the
house plan changes and every 15 minutes), any conditions, and one action:

- **`plan_window`**: devices on from a start to an end. Each end is a time of day (with days),
  the time of an entity + offset (wake-ups, departures, the sun; the earliest of several), or
  minutes counted from the other end (a charging time, a length). Examples: floor heating
  −20/+20 min around Dad's and Mum's wake-up “only if the bathroom is below 22 °C”; the Leaf
  charged 30 min before its first departure; lights from sunset + 30 to sunrise − 30.
- **`upsert`** for a single moment (a time, or the time of an entity + offset).

Rules plan tasks ahead, so the house plan shows them and the executor runs them reliably.
Planning again with nothing changed changes nothing (`unchanged`), so rules may run often.
Reactions at the moment itself (without planning) use ordinary triggers; person device triggers
(“wake-up”, “departure” with an offset) are not needed for now.

### 3.9 Alarms

- No daily summary: the house plan on a dashboard is checked by eye.
- **Android**: in the evening (a time in the person's settings) the system alarm is set for the
  person's wake-up of tomorrow, once a day. If the wake-up moves after that, a notification
  asks to fix the alarm (Android does not let apps change or delete an alarm).
- iPhone: no alarm for now (iOS does not let apps set alarms).

## 4. Screens (own dashboard card)

1. **Family schedule**: a week, one colour per person; create and edit events.
2. **Event form**: title, calendar, start/end, repeat, kind; for trips: trip, riders,
   driver, car, travel time. Fields appear only when needed.
3. **Weekly timetable**: the table above.
4. **House plan**: what the house will do and why; tap a wake-up to move or cancel it.

Until the card exists, basic fields are edited in the standard Calendar panel and the
trip fields with an action form.

## 5. What Home Assistant 2026.10 allows (checked in its source)

- Calendars can create, update and delete events, including recurring ranges
  (`calendar/event/create|update|delete`, `recurrence_range`).
- Creating an event does not return its id; our own calendars do not need it.
- Calendar changes can be subscribed to (`calendar/event/subscribe`).
- An integration can ship its own dashboard card (`frontend.add_extra_js_url`).
- Device triggers with options (offsets) are a standard feature of integrations.

## 6. Steps

1. ✅ **Data**: people (from People) and cars as devices with settings; person calendars with
   trip fields; a form action for trip fields.
2. ✅ **House plan**: wake-ups and departures, cancellations, the “House plan” calendar,
   anchor sensors, Android alarm.
3. ✅ **Rules**: the device trigger “time to plan”, the action `plan_window` (instead of
   blueprints), `upsert` → `unchanged`.
4. **Weekly timetables**.
5. **Card**: family schedule, event form, timetable, house plan.
6. **Moving the real house over**: floor heating → lights → Leaf, the old YAML planner
   running in parallel until the new one has proved itself.

Each step ends tested (automated tests + the test Home Assistant).
